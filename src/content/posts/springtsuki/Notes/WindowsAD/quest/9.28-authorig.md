今天在 AD 的属性编辑器里遇到了 `authOrig`：它似乎和“谁可以给这个组发邮件”有关，但编辑器又提示没有注册的编辑器能处理此类型。继续追问后发现，真正需要先弄清的不是“怎样强行改这个属性”，而是**收件限制、组成员关系和发件限制分别管哪一段邮件流**。

> 本篇是概念与配置思路笔记，不属于 Windows AD PowerShell 指令章节。以下的组名与账号均为示意，**没有在生产 Exchange 环境执行任何更改**。不同版本的本地 Exchange / Exchange Online，管理中心界面可能略有差异。

# 一、先把几个对象分开

| 对象 | 有没有自己的邮件地址 | 邮件发到这里会怎样 |
|---|---|---|
| AD 普通安全组 | 不一定 | 仅有 AD 组身份，不代表能收邮件 |
| 通讯组（Distribution Group） | 有 | Exchange 展开成员，把邮件投递给符合条件的成员；它通常不是每个成员共用的“一个邮箱” |
| 邮件启用的安全组 | 有 | 既可用于授权，也可用作邮件组地址；邮件收发仍由 Exchange 处理 |
| 共享邮箱 | 有，而且有实际邮箱 | 邮件保存在共享邮箱里，由获得权限的人打开；不是“发到组地址后每人各收一份” |

因此口语里的“组邮箱”很模糊：需要先确认对方说的是**通讯组地址**，还是**共享邮箱**。本文讨论的 `authOrig` 场景主要是前者。

# 二、`authOrig` 是什么

`authOrig` 是 Exchange 使用的收件限制相关 AD 属性，对应 Exchange 的 `AcceptMessagesOnlyFrom`：**这个收件对象允许哪些具体发件人给它发信**。它可以出现在通讯组或邮箱等收件对象上；Exchange 在处理邮件时读取相关设置并决定是否接受，而不是由 AD 本身投递邮件。

这里有个容易漏掉的关键区别：

| 想允许谁发给某个收件对象 | Exchange 管理属性 | 相关 AD 属性 |
|---|---|---|
| 某几个具体用户/邮箱 | `AcceptMessagesOnlyFrom` | `authOrig` |
| 某个组的所有成员 | `AcceptMessagesOnlyFromDLMembers` | `dLMemSubmitPerms` |
| 用户与组成员混合 | `AcceptMessagesOnlyFromSendersOrMembers` | Exchange 管理上述限制的组合 |

因此，**“允许 B 组成员给 B 通讯组发邮件”不等于只往 `authOrig` 填 B 组 DN**。组成员许可对应 `dLMemSubmitPerms`；应该通过 Exchange 的“传递管理 / Delivery management”或 Exchange PowerShell 配置，而不是直接猜 AD 属性该填什么。

“在 AD 属性编辑器中没有注册的编辑器能处理此类型”也**不等于**你没有权限，或者此功能只能在图形界面设置。AD 属性编辑器不适合作为管理这些 Exchange 收件限制的主要入口；用 Exchange 管理工具更容易看到真实的配置语义、做校验并避免覆盖已有允许列表。

如果只是想从 AD 侧**只读核对**，可以查询原始属性；返回值通常是对象 DN，未设置时可能为空：

```powershell
Get-ADGroup -Identity 'Org-B' -Properties authOrig,dLMemSubmitPerms |
    Select-Object Name,authOrig,dLMemSubmitPerms
```

这里使用的是 AD 模块，适合辅助观察；真正修改、验证“谁能发给该组”时，仍以 Exchange 管理工具展示的收件限制为准。

> 另一个常见设置是 `RequireSenderAuthenticationEnabled`：只接受组织内经过身份验证的发件人。它与“只允许指定的 B 组成员发送”不是同一个条件；勾了“仅组织内”并不等于已经隔离 B、C 两个部门。

# 三、把“B 组内互发”拆成两件事

假设 B 和 C 各有一个通讯组地址，成员的个人邮箱分别是 `B1`、`B2`、`C1`；管理者 `A1` 可能需要发送通知。

**第一件事：谁能发给 B 的通讯组地址？**

- B 通讯组的允许发件人可以包含 **B 组成员**；如果管理者要给 B 组群发，再额外允许 `A1`。
- C 通讯组同理，可以允许 **C 组成员**，按需额外允许 `A1`。
- 这限制的是发送到 `B组@...`、`C组@...` 这些**组地址**的邮件。

**第二件事：B1 的个人邮箱可以给谁发？**

- `B1 → B2` 是发给 **B2 的个人邮箱**，不会因为 B 通讯组设置了收件白名单就自动受限。
- `B1 → C1` 也是发给 **C1 的个人邮箱**；如果只限制两个通讯组的收件人，B1 仍可能直接发给 C1。
- 要让“B1、B2 只能给 B 成员发邮件”成为完整政策，还得在 **Exchange 邮件流规则（Transport Rule）**层面约束发件人和收件人，或者按业务需求配置每个个人邮箱的收件限制。后一种是“每个邮箱分别管谁能给它发”，维护成本通常更高，不是统一的发件人策略。

| 邮件方向 | 只设置 B/C 通讯组的收件白名单后 |
|---|---|
| `B1 → B 通讯组地址` | 如果 B 成员被允许，可投递 |
| `B1 → C 通讯组地址` | 如果 C 只允许 C 成员，可被拒绝 |
| `B1 → B2 个人邮箱` | **不受 B 通讯组白名单直接限制** |
| `B1 → C1 个人邮箱` | **也不受 C 通讯组白名单直接限制**；这是最容易漏掉的路径 |

## 方案一与方案二

| 场景 | B/C 通讯组的收件设置 | B/C 成员个人邮箱的发送设置 |
|---|---|---|
| 方案一：组内互发，还能发给管理者 `A1` | B 允许 B 成员与需要向 B 群发的管理者；C 同理 | B 成员允许发给 B 成员及 `A1`；C 成员允许发给 C 成员及 `A1` |
| 方案二：严格组内互发 | B 只允许 B 成员；C 只允许 C 成员 | B 成员只允许发给 B 成员；C 成员只允许发给 C 成员 |

注意方向：**“A1 能给 B 通讯组发邮件”**与**“B 成员能给 A1 发邮件”**是两项独立的授权，不能只配置一边就推断另一边也成立。如果 A1 本身也在 B/C 中，规则匹配可能重叠，需要另行设计。

# 四、如何通过 Exchange 管理，而不是直接改 AD 属性

查看一个通讯组当前允许谁发信（在 Exchange 管理 Shell 中）：

```powershell
# 只读查询；Org-B 是示意名称
Get-DistributionGroup -Identity 'Org-B' |
    Format-List Name,PrimarySmtpAddress,RequireSenderAuthenticationEnabled,AcceptMessagesOnlyFrom,AcceptMessagesOnlyFromDLMembers,AcceptMessagesOnlyFromSendersOrMembers
```

如果确实要让 B 组成员向 B 的组地址发信，以下是**示意性配置**；执行前必须先核对真实对象、已有白名单和变更审批：

```powershell
# 示例：将 Org-B 的组成员加入 Org-B 组地址的允许发件人
Set-DistributionGroup -Identity 'Org-B' -AcceptMessagesOnlyFromDLMembers @{Add='Org-B'}

# 示例：如需额外允许管理者 A1 给 Org-B 的组地址发信
Set-DistributionGroup -Identity 'Org-B' -AcceptMessagesOnlyFrom @{Add='A1'}
```

> 上述示例也可以在 Exchange 管理中心的组“传递管理”中配置。`@{Add=...}` 用于追加；如果直接给属性赋完整的新列表，可能覆盖原有允许项。本文没有执行这些修改。

## 补充：直接用 `Set-ADGroup -Add @{}` 修改 `authOrig`

如果只是学习 AD 原始属性的操作，`Set-ADGroup` **技术上可以**给本地 AD 中的组追加 `authOrig` 值。`authOrig` 存的是**具体发件人对象的 DN**，不是 `A1@...` 这样的邮件地址，也不是用来表示“B 组所有成员”的组 DN。

先只读核对目标组、发件人和现有允许列表：

```powershell
$group = Get-ADGroup -Identity 'Org-B' -Properties authOrig,dLMemSubmitPerms
$sender = Get-ADUser -Identity 'A1'

$group | Select-Object Name,DistinguishedName,authOrig,dLMemSubmitPerms
$sender | Select-Object Name,DistinguishedName
```

确认 `A1` 的 DN 是预期对象后，先预演，再追加：

```powershell
$senderDn = $sender.DistinguishedName

# 预演：不会写入 AD
Set-ADGroup -Identity $group.DistinguishedName -Add @{authOrig=$senderDn} -WhatIf

# 真正追加一个具体发件人；本文没有执行
Set-ADGroup -Identity $group.DistinguishedName -Add @{authOrig=$senderDn}

# 重新读取验证；Set-ADGroup 成功时通常没有输出
Get-ADGroup -Identity $group.DistinguishedName -Properties authOrig |
    Select-Object Name,authOrig
```

如果要撤销刚添加的**这一个** DN，可使用 `-Remove`，不要为了移除一个人而把整项属性清空：

```powershell
Set-ADGroup -Identity $group.DistinguishedName -Remove @{authOrig=$senderDn} -WhatIf

# 审核后才执行；本文没有执行
Set-ADGroup -Identity $group.DistinguishedName -Remove @{authOrig=$senderDn}
```

`-Add` 是追加，`-Remove` 是按值移除；`-Replace` 会替换整项属性，`-Clear` 会清空整项属性。`authOrig` 是多值属性，**不要用 `-Replace` 来“多加一个人”**。重复添加已有 DN 可能报错。特别注意：如果原来没有设置任何允许发件人，添加第一条白名单可能立即收紧该组的收件范围，让其他未被允许的发件人退信。应先确认 `authOrig`、`dLMemSubmitPerms` 和 Exchange 中的完整收件限制，并在测试组验证。

**生产环境仍优先使用 Exchange 管理中心或 `Set-DistributionGroup -AcceptMessagesOnlyFrom @{Add='A1'}`。**直接改 AD 属性绕开 Exchange 管理语义及权限检查；在混合部署、目录同步等场景，属性的管理权属也可能影响更改是否有效或能否保留。微软对目录同步对象的 Exchange 属性管理明确要求使用受支持的 Exchange 收件人命令，而非直接使用 ADUC、ADSI Edit 等工具。这里展示 `Set-ADGroup` 是为了理解 LDAP 属性如何追加，**不是推荐的生产变更流程**。

如果希望“B 成员的个人邮箱只能发给 B 成员”，则应在 Exchange **邮件流 → 规则**中配置：

1. 条件：**发件人是 B 组成员**。
2. 操作：拒绝不符合政策的邮件，并写清退信原因。
3. 例外：**收件人是 B 组成员**；方案一再加“收件人是 A1”。
4. C 组建立对应规则，先在测试模式验证，再考虑正式启用。

这不是“仅禁止发外部域名”：**B1 发给同公司的 C1** 也应属于组外发送。多收件人邮件尤其要测试 `B1 → B2 + C1`、抄送和密送；例外应选“收件人”范围，不要选会因为一个允许对象而放行整封邮件的“任一收件人”或只检查 To/Cc 的条件。

> 邮件流规则由 Exchange 管理中心或 **Exchange PowerShell** 的 `New-TransportRule` / `Set-TransportRule` 配置。本地 Exchange 的规则可存储在 AD 中，但它**不是**某个 AD 用户对象上可用 `Set-ADUser` 设置的“外发白名单”属性。不要把“存储位置在 AD”误解成“用 AD 用户属性编辑器配置”。

# 五、与另外几个概念的边界

| 名词 | 它管什么 | 是否等同 `authOrig`？ |
|---|---|---|
| 通讯组的传递管理（Delivery management） | 谁可以把邮件发给**这个组地址** | 它是 Exchange 配置入口；具体可映射到 `authOrig`、`dLMemSubmitPerms` 等限制 |
| 邮件流规则（Transport Rule） | 邮件经过 Exchange 时，按发件人、收件人等条件执行允许、拒绝等动作 | 否；可用于统一约束个人邮箱发件范围 |
| 组的 ACL / 安全权限 | 对文件、共享、AD 对象等资源的访问授权 | 否；能发邮件不代表能访问共享目录 |
| 联合身份验证 / 联合信任 | 身份与组织间信任相关机制 | 否；不能把通讯组收件白名单理解成联合信任设置 |
| 共享邮箱的“发送为 / 代表发送” | 谁有权以共享邮箱或组的身份发件 | 否；这是发件身份授权，不是“谁可给它发邮件” |

这篇笔记最需要记住的一句话是：**收件对象上的白名单，只约束“谁能发给它”；要限制某个人“只能发给谁”，必须另设针对邮件流的策略。**
