## 今天最主要的四类问题

### 1. 根据名称猜属性含义

`LastLogonDate`、`LastLogonTimeStamp` 和 `LastLogon` 的区别不在于“日期、时间戳、时间”三种显示形式，而在于属性来源、是否复制以及精度。

### 2. 把身份状态混成一层

AD 组成员关系、Windows 登录令牌、Kerberos 票据、现有 SMB 会话和资源 ACL 是五种不同状态。更新其中一层，不代表其他层立即刷新。

### 3. 把一个成功测试当成完整证明

例如 `klist get` 成功只证明 KDC 能为当前会话签发目标 SPN 的票据，不能证明服务端能够解密、应用正在使用该票据或 ACL 已经授权。

### 4. 排障流程缺少收尾验证

不少答案能写出前几条检查命令，但没有写复制详情、事件日志、修复动作以及修复后的重复验证。实际工单必须形成闭环。

## Q2：三种最后登录时间

### 我的回答

- `LastLogonDate` 是最后登录日期。
- `LastLogonTimeStamp` 是最后登录时间戳。
- `LastLogon` 是最后登录时间。
- `LastLogon` 最精确；查询所有 DC 是因为复制可能滞后，尤其要关注 PDC。

### 问题所在

前半部分只是根据名称解释，没有说明真正的技术区别。查询所有 DC 也不是为了等待复制完成，而是因为 `LastLogon` **根本不会在 DC 之间复制**；PDC 并不保存全域唯一、最完整的 `LastLogon`。

### 正确结论

| 属性 | 本质 | 是否复制 | 用途 |
|---|---|---|---|
| `LastLogonDate` | AD 模块把 `lastLogonTimestamp` 转换成易读日期 | 间接依赖可复制属性 | 长期不活跃对象粗筛 |
| `LastLogonTimeStamp` | AD 中的 `lastLogonTimestamp` 原始 FILETIME | 会复制，但更新有意延迟 | 90 天、180 天不活跃粗筛 |
| `LastLogon` | 当前 DC 记录的精确登录值 | **不复制** | 查询每台 DC 后取最大值 |

```powershell
# 粗筛 90 天未登录用户
Search-ADAccount `
    -AccountInactive `
    -TimeSpan 90.00:00:00 `
    -UsersOnly
```

查询一个用户在所有 DC 上的 `LastLogon`：

```powershell
$user = "qianyue"

Get-ADDomainController -Filter * |
    ForEach-Object {
        $result = Get-ADUser `
            -Identity $user `
            -Server $_.HostName `
            -Properties LastLogon

        [pscustomobject]@{
            DomainController = $_.HostName
            LastLogon = if ($result.LastLogon -gt 0) {
                [datetime]::FromFileTime($result.LastLogon)
            }
        }
    } |
    Sort-Object LastLogon -Descending
```

> **重点复习**：`LastLogonDate` 不是一套更粗的独立登录记录，它只是 `lastLogonTimestamp` 的易读转换。

## Q3：已经加入安全组，为什么仍然没有共享权限

### 我的回答

正确写出了：

```powershell
Get-ADGroupMember -Identity QYNET-File-Read -Recursive
Get-ADPrincipalGroupMembership -Identity qianyue

whoami /all
whoami /groups

net use
klist

Get-SmbSession
Get-SmbOpenFile
```

### 做得好的地方

- 知道同时检查 AD 组成员关系和客户端登录令牌。
- 知道旧的 SMB 连接和 Kerberos 票据可能继续保存原身份状态。
- 知道问题不能只在 DC 上检查。

### 关键遗漏

`Get-SmbSession` 和 `Get-SmbOpenFile` 查询的是服务器上的 SMB 会话与打开文件，不是共享 ACL。

共享权限应在**文件服务器**上查询：

```powershell
Get-SmbShareAccess -Name "Public"
```

NTFS ACL 应查询共享对应的本地目录：

```powershell
Get-Acl "D:\Shares\Public" |
    Select-Object -ExpandProperty Access
```

完整排查链：

```powershell
# 1. AD 成员关系与组类型
Get-ADGroup -Identity QYNET-File-Read |
    Select-Object Name,GroupCategory,GroupScope

Get-ADGroupMember -Identity QYNET-File-Read -Recursive |
    Where-Object SamAccountName -eq "qianyue"

# 2. 当前登录令牌
whoami /groups | findstr /i "QYNET-File-Read"

# 3. 当前票据与旧连接
klist
net use

# 4. 在文件服务器上查询共享与 NTFS ACL
Get-SmbShareAccess -Name "Public"

Get-Acl "D:\Shares\Public" |
    Select-Object -ExpandProperty Access
```

判断刷新方式：

- SPN、服务账户或旧服务票据变化：修复根因后可以使用 `klist purge` 验证。
- 用户登录后才被加入新组：`klist purge` 不会重建当前桌面登录令牌，最可靠的方法是注销并重新登录。
- 已建立 SMB 连接：关闭文件后使用 `net use \\server\share /delete`，再重新连接。

> **重点复习**：SMB 会话不是共享权限；共享 ACL 和 NTFS ACL 必须分别检查。

## Q4：复制错误 1722

### 我的回答

已经覆盖 Ping、名称解析、`RpcEptMapper`、TCP 135 和防火墙，并正确指出 Ping 失败不等于服务器关机。

### 需要修正

1. Ping 使用 ICMP，不存在“Ping 的端口”。
2. TCP 135 只负责 RPC Endpoint Mapper；实际 RPC 会话还会使用协商出的动态 TCP 端口。
3. `Get-NetFirewallRule -DisplayName "RPC"` 是精确名称匹配，通常不能完整列出 RPC 相关规则。
4. 动态 RPC 不是简单查一个名为 `Dynamic` 的防火墙规则。
5. 缺少 `repadmin /showrepl`、DCDiag 和事件日志。

### 推荐顺序

```powershell
# 1. 名称与地址
Resolve-DnsName QYNET-CORE02.qy.net
Resolve-DnsName 192.168.254.11 -Type PTR
nltest /dsgetdc:qy.net /force

# 2. ICMP 只作参考
Test-Connection QYNET-CORE02 -Count 2

# 3. 常见 AD 端口与 RPC Endpoint Mapper
Test-NetConnection QYNET-CORE02 -Port 53
Test-NetConnection QYNET-CORE02 -Port 88
Test-NetConnection QYNET-CORE02 -Port 135
Test-NetConnection QYNET-CORE02 -Port 389
Test-NetConnection QYNET-CORE02 -Port 445

# 4. 检查关键服务
Get-Service -ComputerName QYNET-CORE02 `
    -Name RpcSs,RpcEptMapper,Netlogon,NTDS,KDC,DNS

# 5. 查看目标 DC 的入站复制详情
repadmin /showrepl QYNET-CORE02 /verbose

# 6. 验证连通性、DNS 和复制
dcdiag /s:QYNET-CORE02 /test:connectivity /v
dcdiag /s:QYNET-CORE02 /test:DNS /v
dcdiag /s:QYNET-CORE02 /test:replications /v

# 7. 修复后重新验证
repadmin /replsummary
repadmin /showrepl QYNET-CORE02
```

RPC 动态端口在现代 Windows Server 上通常位于高位 TCP 端口范围。TCP 135 成功只表示能联系 Endpoint Mapper，不能证明后续协商的动态端口一定畅通。

还应检查目标 DC 的 `System`、`Directory Service`、`DNS Server` 和 `DFS Replication` 日志。

> **重点复习**：1722 是 RPC 通信链失败，不是“服务器关机”的同义词。

## Q5：DNS、SRV 与 SPN

### 我的回答

正确记住了 `setspn -Q`、`setspn -X` 和 `setspn -S` 的主要作用，但 SRV 查询名称不完整，也没有明确全林范围。

### 正确命令

```powershell
# 1. 查询 Kerberos KDC SRV 记录
Resolve-DnsName -Type SRV "_kerberos._tcp.qy.net"

# 也可以使用 Nslookup
nslookup -type=SRV _kerberos._tcp.qy.net

# 2. 在整个林中反向查询 SPN 所有者
setspn -F -Q HTTP/testweb.qy.net

# 3. 在整个林中检查重复 SPN
setspn -X -F

# 4. 安全添加 SPN
setspn -S HTTP/testweb.qy.net QY\svc_testweb
```

`setspn -U` 用来明确目标是用户账户，在已提供明确域用户名称时通常不是必需项。

`-S` 会先检查重复再添加；`-A` 直接写入，可能制造重复 SPN。重复 SPN 会使 KDC 无法唯一确定应该使用哪个账户密钥，导致票据申请失败或认证异常。

> **重点复习**：SRV 查询必须包含服务和协议标签，例如 `_kerberos._tcp.qy.net`，不能只查询普通域名。

## Q6：Kerberos 认证流程

### 我的回答

已经知道大致顺序：KDC 验证用户、TGT 用于继续申请票据、TGS 签发服务票据、SPN 标识目标服务。

### 需要修正

- KDC 不是“服务票据本身”，而是运行在 DC 上的密钥分发服务。
- SPN 不只是资源名称，而是把服务实例映射到 AD 安全主体。
- 目标服务账户密钥不是交给用户的“访问钥匙”，而是服务端用于解密和验证服务票据的密钥。

### 完整流程

```text
1. 用户登录，客户端向 KDC 的 AS 请求 TGT
                    ↓
2. AS 验证用户，返回 TGT
                    ↓
3. 客户端携带 TGT，并以目标 SPN 请求服务票据
                    ↓
4. KDC 的 TGS 查找 SPN 所属账户，签发服务票据
                    ↓
5. 客户端把服务票据交给目标服务
                    ↓
6. 目标服务使用自身账户密钥解密并验证票据
                    ↓
7. 服务根据用户身份、组信息与资源 ACL 决定是否授权
```

拿到 TGT 只证明用户可以继续向 KDC 申请服务票据。它不证明：

- 目标 SPN 存在且属于正确账户。
- 目标服务能够解密票据。
- 服务在线并接受 Kerberos。
- 共享权限和 NTFS ACL 已授权。

## Q7：阅读 `klist` 结果

### 我的回答与复盘

第一问正确：新登录会话尚未使用 Kerberos 访问服务时，票据缓存可以为空。

第二问的“服务端票据、客户端票据”不准确：

| Server 字段 | 票据类型 |
|---|---|
| `krbtgt/QY.NET` | TGT，用于向 KDC 继续申请票据 |
| `cifs/QYNET-CORE01.qy.net` | CIFS 服务票据，用于访问目标 SMB/CIFS 服务 |

`klist get` 成功可以证明：

1. 当前登录会话能够联系 KDC。
2. 当前主体能够获得 TGT。
3. KDC 能够把目标 SPN 唯一解析到一个主体并签发服务票据。
4. 票据已经进入当前登录会话缓存。

它不能证明：

1. SPN 一定注册在实际运行服务的正确账户上。
2. 目标服务拥有匹配密钥并能解密票据。
3. 应用实际使用了这张票据，而不是回退到 NTLM。
4. 服务在线、业务正常或 ACL 已允许访问。

如果 KDC 能看到重复 SPN，通常会因为主体不唯一而拒绝签发；因此“成功签发后仍完全不能说明是否重复”不够准确。但 DC 复制不一致时，仍应结合 `setspn -X -F` 检查全林状态。

## Q8：`klist purge` 的边界

### 我的回答

> 它清的是 Kerberos 票据，不是登录令牌。必须注销，或者创建新的登录会话。

### 复盘

核心判断正确，但处理流程还应补全：

1. 先确认 AD 中的新组成员关系已存在并已复制。
2. 使用 `whoami /groups` 检查当前登录令牌。
3. 如果令牌缺少新组，注销并重新登录。
4. 关闭已打开文件，再清理旧 SMB 连接。
5. 修复 SPN 或服务身份后，才使用 `klist purge` 排除旧票据。
6. 重新连接资源并检查新票据和权限。

```powershell
whoami /groups
klist
net use

net use \\QYNET-FS01\Public /delete
klist purge
```

`klist purge` 不会重建当前桌面会话的本地访问令牌，也不会自动保证所有应用重新建立连接。

## Q9：票据属于哪一个会话

### 我的回答

- 正确记住 `0x3e7` 通常是 SYSTEM 登录会话。
- 知道票据缓存按登录会话隔离。
- 把 LUID 与 SID、GUID 混在了一起。

### 正确结论

`klist sessions` 用于列出本机登录会话，包括每个会话的 LUID、账户和认证类型。

LUID 是由本机 LSA 分配的 **Locally Unique Identifier**，用于在当前计算机、当前运行周期中标识一个登录会话。它不是：

- 用户或组的 SID。
- AD 对象的 ObjectGUID。
- 全域或全林身份标识。

```powershell
# 当前命令所在登录会话
klist

# 列出所有登录会话
klist sessions

# 查询 SYSTEM 会话
klist -li 0x3e7
```

普通 `klist` 只查看当前命令所属 LUID 的缓存。Windows 服务、SYSTEM、计划任务、远程管理和其他用户分别处在不同登录会话中，因此不会自动显示在当前缓存里。

`klist purge -li 0x3e7` 会清除计算机身份和 SYSTEM 服务使用的票据，可能影响 GPO、LDAP、SMB、服务认证和其他域操作。在 DC 上尤其不应随意执行，但也不是“一执行 DC 就必然爆炸”；应准确描述为高影响操作。

> **重点复习**：LUID 标识本机登录会话，SID 标识安全主体，ObjectGUID 标识 AD 对象。

## Q10：AD 域时间层级

### 我的回答

知道 PDC 与外部 NTP、其他 DC 和客户端之间存在层级，也正确指出让所有成员机访问公网会增加安全和稳定性问题。

### 两个关键错误

1. 不是每个域的 PDC Emulator 都直接配置公网 NTP；默认只让**林根域 PDC Emulator**位于整林时间层级顶端并对接权威上游。
2. 时间不是由 PDC 通过 GPO“下发”到其他计算机；GPO 可以配置 W32Time，但实际同步由 Windows Time 服务按照域层级和选择算法完成。

```text
权威外部 NTP / 组织内部时钟
                ↓
林根域 PDC Emulator
                ↓
子域 PDC Emulator与其他合适的上级 DC
                ↓
其他域控制器
                ↓
成员服务器与客户端
```

普通成员默认使用 `NT5DS`，从域层级选择时间源。这样可以：

- 保持全林时间一致。
- 使用域内经过身份验证的时间同步。
- 避免每台设备依赖公网与外部 DNS。
- 避免形成混乱或循环的时间拓扑。

## Q11：分析实验环境的时间状态

### 我的回答

正确识别了 `Local CMOS Clock`、林根域 PDC 以及配置前要检查 UDP 123、DNS 和已有配置。

### 需要修正

`Type: NT5DS` 不表示“NT5DS 的来源是本地 CMOS”。它表示 W32Time 正尝试从 AD 域层级选取时间源；由于该服务器本身就是林根域 PDC，层级上方没有其他域时间源，最终退回到本地硬件时钟。

`Stratum: 1` 也不能单独证明连接了外部硬件时钟。本机以 `LOCL` 作为 RefID 时，也可能把自己作为低层级时间源播发。应同时检查：

- `Source`
- `ReferenceId` / `RefID`
- `Last Successful Sync Time`
- `/query /peers`
- Time-Service 事件日志

### 配置前检查

```powershell
Get-ADDomain | Select-Object DNSRoot,PDCEmulator
Get-ADForest | Select-Object RootDomain

w32tm /query /source
w32tm /query /status
w32tm /query /configuration
w32tm /query /peers

Resolve-DnsName ntp.aliyun.com
w32tm /stripchart /computer:ntp.aliyun.com /samples:5 /dataonly
```

当前实验 VM 无法解析 `ntp.aliyun.com`，所以正式配置前还需要先修复外部 DNS 解析，或使用组织内部可解析的权威时间源。

### 配置命令

以下命令只作复习，本次训练没有在 VM 上执行：

```powershell
w32tm /config `
    /syncfromflags:manual `
    /manualpeerlist:"ntp.aliyun.com,0x8" `
    /reliable:yes `
    /update

Restart-Service W32Time

w32tm /resync /rediscover

w32tm /query /source
w32tm /query /status
w32tm /query /peers
w32tm /query /configuration
```

原回答中分两行执行 `net stop w32time` 与 `net start w32time` 也能工作；在 PowerShell 笔记中使用 `Restart-Service W32Time` 更直观。还遗漏了重新同步与 `/peers`、`/configuration` 验证。

## Q12：Web 服务从 Kerberos 回退到 NTLM

### 我的回答

正确判断最可能与 SPN 缺失、绑错账户或重复有关，也想到了浏览器配置和时间偏差。但只写了三条检查命令，尚未形成可执行流程。

### 完整排查链

#### 第一步：从实际客户端确认名称与 KDC

```powershell
Resolve-DnsName testweb.qy.net

Resolve-DnsName -Type SRV "_kerberos._tcp.qy.net"

nltest /dsgetdc:qy.net /KDC /force
```

目的：确认客户端访问名称正确，并能找到可用 KDC。Kerberos 请求的 SPN 与用户实际输入的主机名有关，不能只检查服务器本机名称。

#### 第二步：主动请求目标服务票据

```powershell
klist get HTTP/testweb.qy.net
```

目的：区分“KDC 无法签发票据”和“已经签发，但应用没有使用或服务端无法验证”。

#### 第三步：查询 SPN 的唯一所有者

```powershell
setspn -F -Q HTTP/testweb.qy.net
setspn -X -F
setspn -L QY\svc_testweb
```

预期：`HTTP/testweb.qy.net` 只注册在实际运行 IIS 应用程序池的账户上。

#### 第四步：核对 IIS 实际运行身份

```powershell
Invoke-Command -ComputerName TESTWEB -ScriptBlock {
    Import-Module WebAdministration

    Get-ChildItem IIS:\AppPools |
        Select-Object Name,
            @{Name="IdentityType";Expression={$_.processModel.identityType}},
            @{Name="UserName";Expression={$_.processModel.userName}}
}
```

目的：确认文档中写的 `QY\svc_testweb` 与服务器当前实际配置一致。SPN 在正确名字下但服务使用另一个账户时，服务仍无法解密票据。

同时检查 IIS 是否启用了 Windows Authentication、`Negotiate` 是否位于 `NTLM` 之前，以及浏览器是否允许对该站点执行集成 Windows 身份验证。浏览器配置确实可能造成回退，但应在 DNS、SPN 和服务身份核对后，用客户端与 KDC 日志证明，而不是只凭猜测。

#### 第五步：检查时间与票据缓存

```powershell
w32tm /query /source
w32tm /query /status

klist
```

修复 DNS、SPN 或服务身份后，再清除当前测试会话的旧票据：

```powershell
klist purge
```

关闭并重新打开浏览器，重新访问 FQDN。

#### 第六步：检查 KDC 事件

```powershell
$startTime = (Get-Date).AddMinutes(-30)

Get-WinEvent -FilterHashtable @{
    LogName   = "Security"
    Id        = 4768,4769,4771,4776
    StartTime = $startTime
} |
    Where-Object Message -Match "qianyue|svc_testweb|HTTP/testweb.qy.net" |
    Select-Object TimeCreated,Id,Message
```

重点：

- 4768：TGT 请求。
- 4769：Kerberos 服务票据请求。
- 4771：预身份验证失败。
- 4776：NTLM 凭据验证，可帮助确认仍在回退。

#### 第七步：形成验证闭环

```powershell
klist | findstr /i "HTTP/testweb.qy.net"

klist get HTTP/testweb.qy.net
```

最终应同时证明：

1. 客户端缓存出现目标 HTTP 服务票据。
2. DC 记录成功的 4769。
3. 不再为该访问路径持续产生 4776。
4. Web 访问正常，服务端没有 `KRB_AP_ERR_MODIFIED` 或解密错误。
5. SPN 在全林中唯一，并属于服务实际运行账户。

> **重点复习**：Kerberos 回退排障不能停在 `setspn -Q`。必须把 DNS/KDC、票据签发、SPN 所有者、服务身份、客户端缓存和事件日志串成闭环。

## 下午闭卷加练：从命令记忆到排障判断

下午在聊天中连续练习了命令和故障判断。以下记录的是**当时的作答与纠正**，不是在 VM 上重新执行后的输出。和上午相比，常用命令已经能较快写出；剩下的主要问题是属性拼写、查询范围，以及把不同层面的状态混为一谈。

### 一、闭卷命令记录

| 题目 | 当时的作答 | 结果与纠正 |

| 查看某 DC 复制详情 | `repadmin /showrepl DC01` | ✅ 正确；需要更详细信息时加 `/verbose`。 |

| 按 SPN 反查所有者 | `setspn -Q HTTP/testweb.qy.net` | ✅ 正确。需要明确查整林时，再考虑 `-F` 范围。 |

> **命令口诀**：`-Filter` 决定**找哪些对象**；`-Properties` 决定**额外取回哪些属性**；`Select-Object` 决定**最终显示哪些列**。属性名记不清时，可先把对象保存到变量，用 `Get-Member -MemberType Properties` 或 `Format-List *` 核对，不需要硬猜。

完整的 IT 部门筛选命令：

```powershell
Get-ADUser -Filter 'Enabled -eq $true -and Department -eq "IT"' `
    -Properties Department |
    Select-Object Name, SamAccountName, Department
```

纯 PowerShell 查询五个 FSMO 角色：

```powershell
Get-ADForest | Select-Object SchemaMaster, DomainNamingMaster
Get-ADDomain | Select-Object PDCEmulator, RIDMaster, InfrastructureMaster
```

### 二、概念与故障题记录

| 场景 | 当时的思路 | 复盘要点 |
|---|---|---|
| 刚加组却访问共享被拒绝 | 提出 SPN、Kerberos、ACL；用 `setspn -Q`、`klist` 排查 | △ **第一步漏了当前登录令牌**。先核对 AD 成员关系、组是否为 `Security`，再在客户端用 `whoami /groups`；最后核对共享权限和 NTFS ACL。出现认证错误线索时才深入 SPN。 |
| DC 的 `IsGlobalCatalog=False` | 不是故障；该 DC 仍可服务本域，不能提供 GC 的跨域搜索 | ✅ 基本正确。多域林中还要考虑通用组成员关系和可用 GC。 |
| FSMO 的五个角色 | 林级：架构、域命名；域级：PDC、RID、基础结构 | ✅ 全对。 |
| 在线 DC 正常退役 | 选择 `transfer` | ✅ 正确。先验证目标 DC 与复制，再转移、核验角色、正常降级；不要直接删除 VM。 |
| 复制报 1722 | 先查 DNS 解析与 IP 连通；随后想到 LDAP 和 SMB | △ 1722 要优先想到 **RPC**：DNS → 网络 → TCP 135 → 动态 RPC 端口/防火墙/服务。LDAP 与 SMB 在对应故障中再查；Ping 通也不能证明 RPC 通。 |
| 根域 PDC 时间源是 `Local CMOS Clock` | 表示本机时钟；正式环境应对接权威 NTP | ✅ 方向正确。它表示当前使用本机时钟，不能仅凭名称断言硬件时钟正在可靠校准。 |
| 入组后 `klist purge` 仍无权限 | 应注销或重启，让“Windows 凭据同步” | △ 处理方向对，但原因是**重新登录才能重建包含新组 SID 的访问令牌**；不是“凭据同步”。通常注销重登即可，不必重启。 |
| 成员机比 DC 快 12 分钟 | 怀疑 Kerberos 时间偏差；用 `w32tm /query /source` 查时间源 | ✅ 正确。这里是票据验证的时间偏差，不等于密码错误。 |
| 用通讯组给文件夹授权 | 指出应使用 `Security`，不是 `Distribution` | ✅ 正确。`GroupCategory` 必须核对。 |
| 组作用域与 AGDLP | 知道 `DomainLocal` 对本域资源授权、`Global` 组织本域用户；应用题开头一度写反，随后自行改正 | △ 固定链条：**用户 → Global → DomainLocal → 资源权限**。新员工只加入 Global，已有 ACL 不用修改。 |
| `replsummary` 正常，但 DC02 暂时查不到 DC01 新建的用户 | 不会立刻全林强制同步；注意多站点链路压力，业务紧急时需处理 | ✅ 风险意识很好；仍应先核对对象、查询的 DC、分区、复制方向和站点链路，再决定是否做最小范围复制。 |

共享权限题可以用这一条链复述：

```text
AD 组成员关系 → 当前登录令牌（whoami /groups）
               → 共享权限（Get-SmbShareAccess）
               → NTFS ACL（Get-Acl）
```

`klist purge` 只清 Kerberos 票据，不会重建当前桌面登录会话的访问令牌。登录后才加入新组时，先注销重登，再检查 `whoami /groups`。现有 SMB 连接也可能需要关闭并重连。

### 三、本次压轴：多站点复制不能“一键全推”

`repadmin /replsummary` 没有失败，只说明当前摘要没有发现复制错误，**不保证新对象已经到达每一台 DC**。尤其多站点可能有复制计划与链路成本。不要因某台 DC 暂时查不到用户，就直接执行：

```powershell
repadmin /syncall /AdeP
```

这里 `/A` 涉及所有命名上下文，`/d` 使用 DN 标识，`/e` 把范围扩展到跨站点，`/P` 使用推送方向。组合执行**可能显著增加站点间流量**，但不应机械地说“必然压满链路”。业务着急也应先定位，再选最小范围。

建议先明确对两台 DC 查询，而不是依赖当前默认 DC：

```powershell
$newUserSam = "newuser"  # 改成刚创建的用户登录名

Get-ADUser -Identity $newUserSam -Server DC01
Get-ADUser -Identity $newUserSam -Server DC02

repadmin /showrepl DC02
```

如果确认对象在 DC01，且需要让 DC02 立即取得 `DC=qy,DC=net` 分区的变化，再评估是否针对性复制：

```powershell
# 目标 DC 在前，源 DC 在后
repadmin /replicate DC02 DC01 "DC=qy,DC=net"
```

> **重点复习**：先定位对象和复制方向，再选最小范围；`/syncall /AdeP` 不是日常“刷新按钮”。

## 明日开始前的快速复习

不看答案，尝试口述下面十三句话：

1. `LastLogonDate` 是 `lastLogonTimestamp` 的易读转换。
2. `LastLogon` 不复制，所以精确查询要遍历所有 DC 并取最大值。
3. `Get-SmbSession` 不是共享 ACL；共享 ACL 使用 `Get-SmbShareAccess`。
4. Ping 使用 ICMP，没有所谓“Ping 端口”。
5. LUID 标识本机登录会话，不是 SID 或 ObjectGUID。
6. `klist get` 成功不证明服务能解密票据或 ACL 已授权。
7. 默认只有林根域 PDC Emulator 对接外部权威时间源。
8. Kerberos 回退要检查 DNS、KDC、SPN、服务身份、票据与事件日志。
9. `-Filter` 找对象，`-Properties` 取额外字段，`Select-Object` 控制输出。
10. 刚加组却无权限：先查登录令牌，再查共享权限与 NTFS ACL。
11. 1722：DNS → 网络 → RPC 135 → 动态 RPC 端口与服务。
12. AGDLP：用户 → Global → DomainLocal → 资源权限。
13. 多站点复制先选最小范围；`/e` 跨站点、`/P` 推送，不要无差别使用 `/syncall /AdeP`。
